TASK 01

Postal Codes: A Useful First Tool

Objective

Build an MCP server that lets a client retrieve Norwegian postal-code data from the postnumbers table or the supplied CSV file.

A natural-language client should be able to answer: “List postal codes and districts in Tysnes kommune.”

Minimum contract

  • Expose at least one discoverable MCP tool.
  • Accept a postal code, district, municipality, or similar filters.
  • Return matching code, district, municipality, county, and coordinates where available.
  • Reject a request with no filter instead of scanning the whole table by accident.
Choose a data source: query PostgreSQL, or read reference_data/Postnummer_med_koordinater_utf8.csv directly. Both routes should expose the same useful MCP tool contract.

TASK 01

Postal Codes: Tutor Hints

1 Start small

First make a single exact postal-code lookup work. Only then introduce optional filters.

2 Let types teach

A numeric postal-code filter and text filters need different validation and query parameters.

3 Parameterise

For PostgreSQL, build SQL conditions and bound parameters separately. Never interpolate a user-supplied value into SQL.

Inspect your chosen source first


SELECT postnummer, poststed, kommune, fylke,
       latitude, longitude
FROM postnumbers
WHERE UPPER(kommune) LIKE '%TYSNES%';

CSV route: read the UTF-8 file once, identify its headers and delimiter, then normalise text before filtering.

Definition of done

  • ✓ Tool appears in MCP Inspector.
  • ✓ A municipality search returns sensible rows.
  • ✓ Empty filters produce a clear error.
  • ✓ An LLM client can use the tool for Tysnes.

TASK 02

OAuth: Protect an MCP Service

Objective

Protect an HTTP MCP endpoint so only callers with a valid Azure AD / Microsoft Entra ID Bearer token can use its tools.

Your MCP server is a resource server. It validates tokens; it does not mint them.

Minimum contract

  • A missing token returns 401 Unauthorized.
  • An invalid or expired token returns 401 Unauthorized.
  • A valid token reaches protected MCP tools.
  • Provide one small tool, such as whoami or echo, to prove the boundary works.

TASK 02

OAuth: Token Journey

What to validate

  • Bearer token is present.
  • Signature matches Entra's public JWKS key.
  • Audience is your API identifier.
  • Issuer is your tenant and expiration is valid.

Configuration to keep outside code

  • Tenant ID
  • Client / application ID
  • Audience (often api://<client-id>)
  • Client secret, if a test client uses client credentials

TASK 02

OAuth: Tutor Hints

Work outside-in

  1. Start with the shared training app registration and its API audience.
  2. Make the unauthenticated endpoint consistently return 401.
  3. Obtain a real access token using a suitable OAuth flow.
  4. Validate it before dispatching MCP requests.
A JWT may look well formed but still be wrong for your API. Signature alone is not enough: check audience, issuer, and expiry.

Definition of done

  • ✓ No Authorization header gives 401.
  • ✓ A fake token gives 401.
  • ✓ A valid token can initialise MCP.
  • ✓ A protected tool returns a successful response.
Do not put client secrets in the repository or a browser application. Use a local environment file excluded from Git or a secret manager.

TASK 03

Consultant Maps: From Tools to Decisions

Objective

Create an MCP service and client that help a sales team find consultants and visualise their locations on a map of Norway.

Example request: “Show consultants in Bergen with at least two years of Python experience.”

Minimum contract

  • Return consultant identity, skills, postal area, latitude, and longitude.
  • Support filters such as technology, experience, county, municipality, or postal district.
  • Plot every returned consultant as a map point.
  • Make the user-facing question and resulting map feel connected.

Server questions

  • Which tables provide a consultant's postal area?
  • Where do skills and assignment experience live?
  • Which rows lack coordinates, and how should you handle them?
  • Which filter combinations are safe and useful?

Client questions

  • Can the map explain each marker with a tooltip or popup?
  • How does the view react to zero results?
  • Will overlapping markers remain understandable?
  • Can a direct client call work before adding an LLM loop?

TASK 03

Consultant Maps: Tutor Hints

1 Prove the join

Write and inspect a database query that returns a few named consultants with non-null coordinates before introducing MCP.

2 Keep tool data plain

Return JSON-friendly rows. A map client should not need to decode presentation-oriented text to find coordinates.

3 Add the LLM last

First call the tool directly from the client. Then let an LLM choose arguments from a natural-language request.

Useful additional tools: list technologies, consultant counts by county, current assignment status, or assignment history. They give a model better context for forming a search.

Definition of done

  • ✓ Map displays returned consultant locations.
  • ✓ A technology filter changes the plotted set.
  • ✓ Empty results and missing coordinates are handled cleanly.
  • ✓ A natural-language request produces a relevant map.

Stretch Goals

Postal codes

Add a resource that describes the data source, or a tool that finds the nearest postal area from coordinates.

OAuth

Enforce an application role or advertise OAuth protected-resource metadata for clients that support discovery.

Consultant maps

Find consultants near a client by calculating geographic distance, then expose the result as a tool.

Keep the principle from every task: expose a narrow, well-described capability; validate it independently; then compose it into a richer experience.
